# Требования Codex Companion — 0.2.7

Штатные вкладки Codex в текущем VS Code; Windows, официальные OpenAI
26.1007.21434 и 26.1021.22027. Собственный чат/новые провайдеры/публикация
не входят в проект. 0.2.6 принята Main и локально установлена 25 октября 2026.
0.2.7 принята Main и локально установлена для 26.1021.22027; подробности — docs/HANDOFF.md.

## Открытые чаты

Текущие панели окна, названия/статусы, title search, waiting/error первыми,
различимые представления, выбор пустой вкладки. Live refresh сохраняет запрос.
Фокус — только существующий panelId после двух сверок instance/thread/route;
закрытый чат не переоткрывать. Опрос только пока список видим, без второго
App Server и без наблюдения за другими клиентами. Строгой cwd per-thread
фильтрации метаданные bridge не обеспечивают.

Команды `codexCompanion.nextWaitingChat` (следующая ожидающая панель) и
`codexCompanion.nextAttentionChat` (сначала ожидание, затем ошибки) назначаемы
на клавиши, но без привязок по умолчанию. Счётчик `[? N]` скрыт при нуле и
обновляется событиями текущего окна, без постоянного опроса; он не зависит от
дедупликации уведомлений. Обновление счётчика — по событиям/вкладкам/совместимости
текущего окна.

## Черновики

Новые HOME вкладки Companion с UUID имеют отдельные текстовые черновики,
которые сохраняются после переключения и перезапуска. В 26.1007 scopeKey
получает одна ветка Fv, в 26.1021 — chunk composer-scope. Нативные
model/effort/identity/saved/thread/send пути и специальная блокировка
homeDraftKey остаются прежними.
Общий legacy текст не удаляется и не размножается; доступен командой
«Открыть прежний общий черновик». Сохранённые чаты и их модели/черновики не менять.

Изображения из буфера между открытыми вкладками не смешиваются. Их отсутствие
после cold restart — подтверждённое прежнее поведение, не новая гарантия хранения.
В 0.2.6 сохранение не реализовано: исследование показало, что изображение живёт
в памяти отдельно от persisted text, поэтому нужен отдельный нативный target.

## Квоты

До двух наиболее израсходованных фактических серверных окон +N, логотип Codex.
Кредиты также показываются в нижней кнопке рядом с лимитами: баланс округлён
до целого, безлимит обозначен ∞; отсутствующее значение не подменяется нулём.
В tooltip/report кредиты сохраняют точность сервера.
Все окна/имена/кредиты, used/remaining, даты с UTC offset, свежесть и reset в
tooltip/report. Порог 90/100% только для свежих данных. Прошедший reset требует
refresh без выдуманного обнуления. Approximate pace с начала окна явно обозначен
и скрыт при несвежих данных. API и quotaMonitor остаются прежними; разбивку по
чатам/проектам и прогноз недавнего расхода не обещать. Функциональность квот
0.2.3 в 0.2.4 не меняется. Сэмплирование/история квот в 0.2.6 не реализованы;
будущий этап — только account-wide с границами reset/аккаунта, без оценок на проект.

## Совместимость и установка

Для 26.1007 остаются manifest/attestation schema 1/2: package + host +
97d/c014/7a, пять файлов и backup
LOCALAPPDATA/codex-companion/patches/26.1007.21434/drafts-v1. Auto legacy
adoption только из проверенного old4 backup + оригинального 7a; старые
файлы/manifest не менять.

Для 26.1021 — schema 3: девять оригиналов — package.json (identity guard),
out/extension.js и семь точных webview chunks (src-622b,
initialize-app-host-services, chatgpt-conversation-page, message-bus,
dynamic-intelligence-dropdown, composer-content, composer-scope). Metadata —
resources/patchBundleManifest-26.1021.22027.json и
patchAttestation-26.1021.22027.json; backup —
LOCALAPPDATA/codex-companion/patches/26.1021.22027/chunks-v1. Новый install
не делает legacy adoption и не трогает старый backup.

Обновление с установленной 0.2.6: прежний принятый engine делает точный restore
исходных файлов OpenAI engine 0.2.6, затем выполняется install 0.2.7; backup `chunks-v1` сохраняется.
Неизвестные/изменённые байты автоматически не восстанавливаются.

Общие правила: известные целые стадии original/history/titles/workflow/drafts;
источники и все цели проверены до записи; unknown/mixed/modified и invalid backup
отказываются. Locks для extension и backup, атомарные записи, post-verify, точный
rollback с сохранением внешних изменений; ошибки неполного rollback сообщать явно.
Full restore возвращает все оригинальные цели, не трогает пользовательские данные;
package identity не переписывается. Downgrade сначала full restore новым engine,
затем старый VSIX/patches. Проверка/отчёт ничего не устанавливают. Unknown версии
автоматически не патчить.

`projectHistoryUi` и `titleRefresh` используют VERIFIED_EDITOR_VERSIONS для
26.1007.21434 и 26.1021.22027. Native source/runtime/manifest/attestation и
backup в 0.2.6 не меняются.

## Сохраняемое поведение

История recent/full/search локального Codex по проекту; мгновенное штатное имя;
проектная пара модель/effort из штатного UI; [~]/[V]/[!]/[?], однократный звук
на новое успешное [V], silent restore. Облачная история и session picker VS Code
не фильтруются. Sandbox/auth/history/права доступа/черновики не переносить и не
удалять. Рабочие окна/задачи не закрывать, не reload и не возобновлять автоматически.

В 26.1021.22027 карточки асинхронных вопросов (`agentMessage.questions`) включают `[?]`.
Неразрешённый запрос ответа сохраняет ожидание при последующих событиях работы;
асинхронная карточка сохраняет его и после успешного завершения turn, без `[V]`
и звука. Обычный текст без структурированных вопросов не распознавать по знакам
препинания. Ошибка или прерывание должны сохранять свой терминальный статус.
Слой 26.1007.21434 сохранён побайтно; это исправление в него не переносилось.

Переход idle → waiting на нативных async-карточках уведомляет «нужен ваш ответ»
(`needs your answer` в английском UI) и играет отдельный короткий синтезированный
`waiting.wav` 0.32 с; прежний звук завершения не меняется. Настройки уведомлений,
окон и звука сохраняются, mute глушит оба сигнала. Счётчик `[? N]` ведёт
WorkflowUi по `onStatusEvent`, независимо от дедупликации уведомлений.
Дедупликация — логический `eventId`: отдельное уведомление на каждый вопрос
внутри одного turn не гарантируется; replay/snapshot молчат.

## Восстановление статусов — 0.2.7

После reload Companion восстанавливает статусы вкладок 26.1021.22027 только по
уже существующим запросам/ответам `thread/read` самой панели. Собственного RPC
или второго App Server, опроса, наблюдения за другими клиентами, сообщений
модели, автоматического reload, возобновления задач и публикации нет.

- Снимок `live:false` обновляет название и счётчик внимания, но не создаёт
  уведомлений и звуков; последующие live-события работают обычно.
- `includeTurns:false` восстанавливает только runtime active flags и
  `systemError`; idle/notLoaded без turns статус не выдумывают.
- Полный `turns`: inProgress → running/waiting, completed → done, failed → error,
  interrupted/cancelled/canceled → idle. Незавершённая цель сохраняется
  (active → running, иначе waiting) и не даёт ложного `[V]`.
- Вопросы сопоставляются только по точному native-конверту ответа и
  `questionItemId`; частичный ответ закрывает только указанные вопросы,
  отклонённое steering чужие вопросы не закрывает.
- Неразрешённые вопросы completed turn удерживают idle или прежнее waiting и не
  считаются надёжным восстановлением. При missing/paginated данных точное
  состояние вопросов неизвестно.
- Записи чтения ограничены 64; проверяются thread/turn, `requestSeq` и live epoch;
  запись очищается по ответу, ошибке, abandon, неудачной доставке и dispose
  webview.
- Слой 26.1007 runtime/metadata побайтно прежний; на 26.1021 меняются только host
  workflow/drafts, остальные webview/pre-workflow стадии прежние.

Следующая работа по статусам — вопросы завершённых/постраничных turn; изображения
и история квот остаются backlog.
