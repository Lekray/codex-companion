# Первая dev-версия Companion

## Принятые решения

После команды «начинай реализацию» проверены установленное расширение и официальный протокол. Пользователь выбрал собственные вкладки Companion, компактный чат, отдельные названия, формат строки квот, кнопки над редактором и восстановление вкладки при отмене закрытия.

Версия: `0.1.0-dev.3`. Среда проверки: Windows x64, VS Code 1.139.1, Codex 26.1007.21434, CLI 0.162.0-alpha.17.2. Сборка — TypeScript, тесты — Node test runner. В продукте нет интеграции DeepSeek или Kimi.

## Проверка интеграции

- Manifest и `out/extension.js` установленного Codex: `chatgpt.newCodexPanel` зарегистрирован; внутренняя реализация открывает custom editor. Заголовок выставляется самим Codex. Публичный API для независимого переименования конкретной вкладки не найден. Это вывод анализа доступной поверхности, не обещание невозможности всех обходных способов.
- `initialize` / `initialized`, `account/rateLimits/read`, `thread/list`, `thread/loaded/list` проверены на настоящем CLI. Отдельный App Server вернул ноль загруженных диалогов при работающем чате в IDE. Companion не использует его для наблюдения за чужими задачами.
- Одно временное обращение к настоящему Codex с read-only sandbox завершилось ответом `OK`; проверены поток текста и `turn/completed`. Задача не просила использовать инструменты.
- Реальный App Server не сохраняет пустой диалог до первого сообщения. Поэтому новая вкладка получает локальный стабильный ID, а thread создаётся при первой отправке.

Источники: [App Server](https://learn.chatgpt.com/docs/app-server), [команды Codex IDE](https://learn.chatgpt.com/docs/ide/commands), [настройки Codex IDE](https://learn.chatgpt.com/docs/ide/settings), [VS Code Webview API](https://code.visualstudio.com/api/extension-guides/webview).

## Реализация

- `src/appServer.ts`: отдельный stdio-процесс на окно, handshake, сопоставление ответов, тайм-ауты, уведомления и server requests; неизвестный запрос не подтверждается. Процесс запускается без shell. Завершение ограничено по времени; при зависании останавливается принадлежащее клиенту дерево процессов Windows.
- `src/session.ts`: независимые локальные имена, создание/чтение/продолжение диалогов, поток ответов, результаты инструментов, ожидание ввода и разрешений, остановка. Загрузка истории не вызывает resume или turn/start. Во время загрузки отправка заблокирована.
- `src/extension.ts`: команды, webview, состояние рабочего пространства, сохранение счётчика, восстановление вкладок, квоты и уведомления. После переподключения открытые вкладки сохраняют уже показанную историю.
- `src/quotas.ts`, `src/formatQuotas.ts`: группы и окна лимитов, индивидуальный лимит расходов и кредиты при наличии; длительности берутся из ответа. Устаревшие данные явно обозначаются.
- `src/webview.ts`, `media/chat.*`: русский/английский интерфейс, CSP, вставка текста через textContent, подтверждение отправки перед очисткой черновика, сохранение ввода во время обновлений.

История меню включает созданные Companion диалоги этого рабочего пространства. При закрытии вкладки задача может продолжаться в фоне; закрытие окна VS Code завершает его App Server. После перезапуска задачи не возобновляются автоматически.

## Проверки

- Core-тесты: 31/31 пройдены. Дополнительно проверены нативные коды клика/скрытия/закрытия/тайм-аута, ошибка запуска уведомления и отмена вспомогательного процесса при завершении расширения.
- Два обычных запуска VS Code с отдельным профилем: две независимые вкладки, переименование, закрытие одной, полный перезапуск, восстановление названия, счётчика и отсутствие автозапуска задач. Стандартный extension-test режим для этой проверки не подходит: VS Code использует в нём память вместо постоянного хранилища.
- Браузерный тест реальных HTML/JS/CSS в Edge: отправка, сохранение черновика до подтверждения, сохранение ответа при обновлениях, ответ на вопрос, отсутствие интерпретации текста модели как HTML. Предпросмотр — `.artifacts/chat-preview.png`, с тестовыми сообщениями.
- Настоящий App Server: чтение квот/истории и временная read-only задача прошли.
- Настоящая сохранённая история: создан отдельный read-only диалог, получен `HISTORY_OK`, процесс App Server завершён и запущен заново. `Sessions.history()` восстановил сообщения; `thread/loaded/list` подтвердил отсутствие загруженной задачи. Тестовый диалог после проверки архивирован.
- Полный UI-прогон в настоящем VS Code с синтетическим stdio-сервером: закрытие работающей вкладки с отменой, продолжение в фоне и возврат через историю, остановка кнопкой и при закрытии, явное отклонение разрешения, ответ на вопрос. Проверены вызовы протокола, отсутствие повторного запуска и отсутствие автоматического разрешения.
- Параллельные открытия проверяются в extension host: два одновременных вызова получают разные номера; счётчик сохраняется после полного перезапуска.
- Windows: тестовый toast найден по своему ID в системной истории уведомлений; затем удалён. Проверка не выводит содержание других уведомлений.
- VSIX собран локально; dev.3 затем установлена в основной профиль по отдельному разрешению пользователя. Публикация не выполнялась.

## Границы проверки

- Нативный клик и переход из свежего баннера подтверждены ручным кликом пользователя и автоматическими проверками состояния двух окон. UI Automation возвращает Access denied для самого баннера, поэтому нажатие выполнялось вручную. Поведение старой записи центра уведомлений после завершения нативного процесса не гарантируется.
- UI подтверждений и закрытия проверен с синтетическими событиями. Настоящий запрос расширенных разрешений от модели в пользовательской рабочей задаче отдельно не проверялся.
- Перезапуск с историей настоящего короткого диалога проверен на уровне App Server; длительная реальная задача, полный перезапуск VS Code и возобновление в одном сквозном сценарии ещё не прогонялись.
- Интерфейс первой dev-версии текстовый. Вложения, встроенные приложения MCP, произвольные MCP elicitation-формы и настройка модели из чата не реализованы. Модель и политики берутся из конфигурации Codex. Неподдерживаемые запросы отклоняются.

## Делегирование

DeepSeek V4.1 Flash (high) получил ограниченный read-only аудит, но завершился по тайм-ауту 420 секунд без проверяемого отчёта. Запуск отмечен `rejected`; интеграционный анализ выполнен Codex. Отдельный агент Codex добавил тесты и выявил гонки отправки, остановки и загрузки истории; основная модель исправила код и повторно запустила проверки.

## Изменения dev.2 и повторная проверка DeepSeek

- Общий флаг `busy` больше не трактуется как работа агента: загрузка истории не вызывает предложение остановить задачу и не отменяет следующую отправку. Ошибка чтения остаётся видна в ленте, но не вызывает уведомление о сбое несуществовавшей задачи.
- При переподключении записи ленты копируются, чтобы запоздалая ошибка старой сессии не меняла массив новой.
- Номер новой вкладки резервируется до асинхронного сохранения. Регрессия была воспроизведена в VS Code: два параллельных открытия ранее создавали две вкладки `Codex 4`.
- После диагностики первого тайм-аута глобальный лимит воркера увеличен до 3600 секунд. Новый DeepSeek-аудит двух файлов завершился за 271,44 секунды. Его два основных замечания воспроизведены отдельными падающими тестами и исправлены. Оценка отчёта `reworked`: формулировка о «потере» сообщения уточнена (черновик оставался, отправка пропускалась), также воркер прочитал два дополнительных файла проекта за пределами назначенной пары исходников. Запуск не изменял файлы.

## Изменения dev.3: подтверждённый клик Windows

Ручной тест выявил реальную потерю события в JS-обёртке: после клика SnoreToast завершился с кодом 0, а node-notifier вернул пустые response/metadata. Собственный адаптер `src/windowsNotifications.ts` теперь читает нативный результат напрямую. В этом вызове передаются только параметры показа, поэтому 0 означает Clicked; 1/2/3 — Hidden/Dismissed/TimedOut и не переводят фокус. Ошибки процесса не превращаются в клик. Вспомогательные процессы завершаются при деактивации расширения.

Контракт сверен с [исходником SnoreToast 0.7.0](https://github.com/KDE/snoretoast/blob/v0.7.0/src/main.cpp). Бинарный файл берётся из уже закреплённой зависимости node-notifier; установленные расширения, ярлыки, реестр и настройки уведомлений пользователя не изменяются. Неиспользуемые Windows-обёрткой параметры wait/timeout удалены; собственный предел процесса — 60 секунд.

После исправления отдельный ручной клик вернул `activated` за 935 мс. Затем пользователь нажал реальное уведомление при открытых двух тестовых окнах. Проверка увидела `source.focused=true`, исходную вкладку `[V] Companion test 1792190838990` и `other.focused=false`. Прогон: `.artifacts/notify-focus-1792190838990`. Тестовые уведомления удалены; тестовые окна закрыты. Стенд использует синтетическую задачу и настоящее Windows-уведомление.

DeepSeek-аудит уведомлений завершился за 59,9 секунды. Подтверждены игнорирование wait/timeout в старой обёртке и её преобразования callback. Предположение о COM-перенаправлении через appID не принято как установленная причина. Оценка reworked: воркер выполнил 10 чтений вместо заданных 8; выводы проверены Codex и ручным экспериментом.

CLI подтвердил `local-companion.codex-companion@0.1.0-dev.3`; установленный runtime совпадает с VSIX. Manifest сравнивался без добавленного самим VS Code блока `__metadata`.
